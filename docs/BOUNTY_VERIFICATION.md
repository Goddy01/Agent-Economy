# Bounty Requirements — Code Verification

This document maps each **Technical Expectation** and **Judging Criterion** to specific files and line-level evidence in the codebase. It was generated by auditing every relevant code file.

## Technical Expectations

### 1. Safe key management and storage for autonomous agents

| Requirement | Evidence in code | Status |
|-------------|------------------|--------|
| **Encryption at rest** | `src/vault/crypto.ts`: `encrypt()` / `decrypt()` use **AES-256-GCM** (lines 37–57, 63–92). Key derived with **Argon2id** (lines 20–31, `argon2.argon2id`, memoryCost 65536). | ✅ Met |
| **Key material zeroed after use** | `src/vault/crypto.ts`: `key.fill(0)` after encrypt (line 50), after decrypt (line 76). `src/vault/KeyVault.ts`: `seedPlain.fill(0); key.fill(0)` after derivation in `registerAgent` (144–145) and in `sign` (193–194). `restore()` zeros seed (line 111). | ✅ Met |
| **No key export API** | KeyVault exposes only: `initialize()`, `restore()`, `registerAgent()`, `getAgentPublicKey()`, `sign()`. No method returns private key, seed, or mnemonic (mnemonic returned once at init for backup only). Agents never receive key bytes. | ✅ Met |
| **HD derivation per agent** | `src/vault/KeyVault.ts`: BIP-44–style path `m/44'/501'/${index}'/0'` (line 139, 189). Each agent gets unique `derivationIndex` (135–139). | ✅ Met |
| **Passphrase from env only** | `src/colony/Orchestrator.ts`: `process.env.MASTER_PASSPHRASE` (35–40). No hardcoded passphrase in repo. `.env` is in `.gitignore`. | ✅ Met |

**Verdict:** **Met.** Key management is centralized in KeyVault + crypto; keys are encrypted at rest, zeroed after use, and never exposed to agents.

### 2. Automated transaction signing without manual input

| Requirement | Evidence in code | Status |
|-------------|------------------|--------|
| **Signing triggered only by agent logic** | Agents call `this.txEngine.executeTransaction(agentId, tx, description)`. Only place that calls `vault.sign()` is `src/transactions/TransactionEngine.ts` line 111, inside `executeTransaction()`, after circuit breakers and simulation. No CLI prompt or human-in-the-loop. | ✅ Met |
| **Passphrase already in env** | Orchestrator constructs `KeyVault(passphrase)` once at startup (Orchestrator.ts 43). No interactive prompt for signing. | ✅ Met |
| **Agents never touch keys** | Grep: `vault.sign` is only in TransactionEngine and MemoLogger. Agents only call `walletManager.buildTransferTransaction`, `txEngine.executeTransaction`, `orca.buildSwapTransactionForMemo`. No agent file imports crypto or calls `decrypt` / raw key APIs. | ✅ Met |

**Verdict:** **Met.** Signing is fully automated: agent decides → builds tx → engine validates and simulates → engine calls vault.sign → send. No manual step.

### 3. Ability to simulate decision-making or execution by an AI agent

| Requirement | Evidence in code | Status |
|-------------|------------------|--------|
| **Simulate decision-making** | Agents implement `decide()` (e.g. Accumulator 45–105, Flipper 48–101) with deterministic rules + optional LLM rationale via `rationaleEngine.explain(decision)` (BaseAgent.ts 107–108). Decisions emitted as `decision` events; dashboard shows them. | ✅ Met |
| **Simulate execution (no tx sent)** | `src/colony/Orchestrator.ts`: `dryRun: process.env.DRY_RUN === 'true'` (line 51) passed to TransactionEngine. `src/transactions/TransactionEngine.ts`: lines 97–106 — when `this.config.dryRun` is true, returns success with `dryRun: true` and **never** calls `this.vault.sign()` or `this.connection.sendRawTransaction()`. Test in `tests/transaction.test.ts` (dry run block) asserts sign and sendRawTransaction are not called when dryRun is true. | ✅ Met |
| **Simulation before every real send** | TransactionEngine lines 84–95: `simulateTransaction()` is always called; if it fails, function returns without signing or sending (lines 85–94). Sign/send only at lines 109–117, after simulation passes and only when not dry run. | ✅ Met |

**Verdict:** **Met.** Decision-making is simulated (rules + optional LLM). Execution can be run in “simulation only” mode (DRY_RUN); when not dry run, every tx is simulated on RPC before sign/send.

### 4. Clear separation of responsibilities between agent logic and wallet operations

| Requirement | Evidence in code | Status |
|-------------|------------------|--------|
| **Agent logic only** | `src/agents/BaseAgent.ts`, `Accumulator.ts`, `Flipper.ts`, `Vault.ts`: Agents hold references to `vault`, `walletManager`, `txEngine`, `memoLogger`. They call: `getBalance()` (→ walletManager.getSolBalance), `walletManager.buildTransferTransaction()`, `txEngine.executeTransaction()`, `orca.buildSwapTransactionForMemo()`, `memoLogger.addMemoInstruction()` / `recordMemo()`. They do **not** call `vault.sign()`, `vault.registerAgent()` (only Orchestrator/walletManager do), or any decrypt/encrypt. | ✅ Met |
| **Wallet/signing only in vault + engine** | `KeyVault`: registerAgent, getAgentPublicKey, sign (and initialize/restore). `WalletManager`: createWallet (→ vault.registerAgent), getSolBalance (→ vault.getAgentPublicKey + RPC balance), buildTransferTransaction. `TransactionEngine`: rate limit, value cap, vault floor, simulate, then vault.sign + send. Only TransactionEngine and MemoLogger invoke `vault.sign()`. | ✅ Met |
| **No raw key handling in agents** | No agent file imports `./vault/crypto` or uses `Keypair.fromSecretKey` / private key bytes. Agents receive only public addresses (from createWallet) and transaction results. | ✅ Met |

**Verdict:** **Met.** Agent code lives in `src/agents/` and only uses wallet/tx APIs. Key storage and signing live in `src/vault/` and `src/transactions/`; agents cannot bypass the engine.

### 4. Scalability: support multiple agents independently

| Criterion | Evidence in code | Status |
|-----------|------------------|--------|
| **Multiple agents** | Three agents: vault, accumulator, flipper (Orchestrator 86–89, 126–129). Each has own wallet via `createWallet(agentId)`. | ✅ Met |
| **Independent wallets** | KeyVault.registerAgent(agentId) assigns unique derivationIndex per agent (KeyVault 136–138). Each agent has distinct public key and balance. Rate limiter is per agentId (RateLimiter used by TransactionEngine). | ✅ Met |

**Verdict:** **Met.** Multiple agents are supported with independent wallets and scalable derivation.
